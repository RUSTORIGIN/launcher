# Client-side anti-cheat: launcher session (design, v1)

Status: slices 1-8 are built (see [Build slices](#build-slices)); enforcement (slice 7) ships switched off. They run on the dev server only, and
the shipped `launcher.cfg` leaves `AcSessionUrl` blank. This file is the contract the launcher, the session
service and the gate plugin are built against.

## Goal and limits

Today anyone can start `RustClient.exe` directly and the server cannot tell. Any check that lives only in
the launcher is therefore optional for exactly the players it is meant for. The launcher session closes
that hole: the game server only lets in players whose launcher holds a live session for their SteamID and
IP, and the launcher's checks travel with that session as evidence.

What it is **not**:

- **Not proof that a client is clean.** The launcher is open source and stays that way. Someone able to
  reimplement this protocol can produce a session without the real launcher. The session raises the cost
  of cheating from "download a tool" to "build and maintain a fake launcher", which filters the bulk of
  casual cheaters. It is one layer next to the server-side OriginAntiCheat, not a replacement.
- **Not a ban reason.** Signals the launcher reports are evidence for the anti-cheat score and for human
  review. A missing session (once enforced) is a kick, never a ban.
- **Not secret.** Everything here may be read by anyone. Nothing in the design depends on hiding it.

## Components

```
Launcher (this repo)                Prod game box
------------------------           --------------------------------------------------
PLAY -> POST /v1/session   --TLS->  session service (small, stdlib only)
        <- session id + key            keeps: steamid, ip, key, last seq, last heartbeat
game runs, every N seconds:                     ^ 127.0.0.1 only: GET /v1/check
  POST /v1/heartbeat (HMAC-signed)              |
                                    OriginSession plugin (Oxide gate)
                                      on join + every 60 s: ok / none / stale / mismatch
                                      shadow mode: log only -> later: kick after a grace period
                                      signals -> OriginAntiCheat as log-only "Launcher" evidence
```

- **Launcher:** `src/AcSession.cs` builds and signs the messages, parses the replies, gathers the
  evidence labels and the hardware id, and runs the session client that `Play` starts (`StartAcSession`
  in `src/WpfLauncher.cs`).
- **Session service and gate plugin:** live in `RUSTORIGIN/plugins`, not in this repo. The Oxide sandbox
  normally keeps plugins away from raw network listeners, so the plugin does not host the endpoint. It
  asks the service over `127.0.0.1` with Oxide's `webrequest`.
- **Address:** a new TLS subdomain (working name `ac.rustorigin.com`) pointing at the prod box. It is
  still to be created. The launcher keeps its rule of TLS 1.2+ only, with no HTTP fallback.

## Protocol v1

All bodies are UTF-8 JSON objects with only string and integer values (no nesting except the `signals`
string array). Field order is fixed by the launcher, but the server must not depend on it: signatures are
computed over the **raw body bytes as sent**, so no canonical re-encoding is ever needed.

### 1. Open a session: `POST /v1/session`

Request (unsigned; there is no secret yet):

```json
{"v":1,"steamid":"76561198000000000","launcher":"1.2.0","nonce":"<32 hex>","t":1760000000,"hw":"<64 hex>"}
```

- `steamid`: the SteamID64 of the Steam account logged in on this PC (read from Steam's registry entry by
  the launcher). It is a **claim**: the server checks it against the SteamID that actually joins.
- `nonce`: 16 random bytes, so two requests in the same second are distinct in logs.
- `t`: the launcher's Unix time; the server only uses it to log large clock skew.
- `hw` (optional, slice 6): the PC's hardware id, lowercase hex `SHA-256("rustorigin-hw-v1:" + MachineGuid)`,
  where MachineGuid is `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` in lower case. Like the SteamID it
  is a claim. The service ignores a malformed value and still opens the session, and a launcher that can't
  read it leaves the field out. See [Hardware id](#hardware-id-slice-6).

Reply:

```json
{"session":"<32 hex>","key":"<64 hex>","heartbeat":30,"ttl":120,"tools":"1=autohotkey,autohotkeyu64;2=..."}
```

- `session` (16 random bytes) and `key` (32 random bytes) are generated by the server per session.
- `heartbeat` is the interval in seconds (the launcher clamps it to 10-300).
- `ttl` is how long the session stays fresh without a heartbeat (clamped to 30-900, and at least twice the
  heartbeat).
- `tools` (optional) holds the tool rules: `<id>=<process>,<process>` joined by `;`. Ids are numbers, and
  process names are lower case without `.exe`. The launcher reports a match only as `tool:<id>`. The list
  lives in a private file on the server (`ac_tools.txt`), so it is not in this repo, the exe or the
  player's config. The field is additive: a launcher that doesn't know it ignores it, and a service that
  doesn't send it gives no tool rules. Anyone holding a session can still read the rules from this reply,
  so this keeps the list out of plain sight; it does not make it secret.

### 2. Heartbeat: `POST /v1/heartbeat`

```json
{"v":1,"session":"<32 hex>","seq":7,"t":1760000210,"game":1,"signals":["tool:autohotkey"]}
```

with the header `X-AC-Sig: <64 hex>` = lowercase hex of `HMAC-SHA256(key, raw body bytes)`.

The server accepts it only when **all** of these hold, and otherwise answers with `ok` 0 and a reason:

1. the session exists and is not expired;
2. the signature matches (constant-time compare);
3. `seq` is greater than the last accepted `seq` (replay protection);
4. `t` is within 120 s of the server clock;
5. the request comes from the same IP that opened the session.

Reply: `{"ok":1,"next":30}`, or `{"ok":0,"reason":"<short code>"}`. On `ok` 0 the launcher opens a new
session. `next` lets the server slow heartbeats down under load.

`signals` are short labels (`[a-z0-9_.:-]`, at most 64 characters each, at most 32 per heartbeat). The
launcher sends a label only when something matched (for example a known macro tool), never a process list.
The labels and the rules that produce them are in slice 5 below.

### 3. Gate check (local only): `GET /v1/check?steamid=<id>&ip=<ip>`

Bound to `127.0.0.1`. Reply `{"status":"ok", ...}` or `none` / `stale` / `mismatch`:

- `ok`: a fresh session exists for this exact SteamID and IP.
- `stale`: one existed, but its last heartbeat is older than `ttl`.
- `mismatch`: there is a fresh session for this SteamID from another IP, or for this IP with another SteamID.
- `none`: nothing.

An `ok` reply also carries the launcher version, `game`, the raw `signals`, the staff-readable `labels`
(tool ids turned back into names), the heartbeat `age` and the `heartbeats` count. When the session was
opened with a hardware id it adds `"hw":"<first 16 hex>"` and `"hw_accounts":[...]`: the other SteamIDs
(at most 16) that hold a session from the same PC, fresh or not, among the sessions the service still
remembers (6 hours after their last heartbeat). Since slice 8, `hw` is the **server-keyed device id**, not
the launcher's value, and a contested session (see [Device id](#device-id-slice-8)) answers `"contested":1`
instead of `hw` / `hw_accounts`.

### Hardware id (slice 6)

The alt-account signal: it shows staff that several accounts play from one PC. It never refuses a session and
is never a ban reason on its own. Since slice 8 the RustRCON panel uses it for one thing beyond review: a
match to the PC of an **actively banned** account kicks and opens a case (shadow mode first, see
[Device id](#device-id-slice-8)). Families, shared PCs and LAN parties
legitimately produce it.

- **Source: the Windows MachineGuid.** It is random per Windows install, so two PCs never share one by
  accident. The SMBIOS UUID was rejected: many boards ship the same generic UUID, which would link strangers.
  MachineGuid changes when Windows is reinstalled, and someone determined can change it; that is acceptable
  for a review signal.
- **Hashed with a Rustorigin prefix** on the PC, so what leaves the PC is not the MachineGuid itself and can't
  be matched against the raw value other software may report. The prefix is public: the hash keeps the id
  out of plain sight, it is not a secret.
- **It is a claim.** The launcher is open source, so anyone can send any value or none. A fake value only
  hides a link; a forged link would need another player's hash, which only appears, shortened, in the staff
  logs on the server.

### Device id (slice 8)

The launcher is unchanged: it still sends `hw` as above. The service never keeps that value. On arrival it
replaces it with `HMAC-SHA256(AC_HW_KEY, "rustorigin-pc-v1:" + hw)`, where `AC_HW_KEY` is a 32-byte secret in
the service's `server.env` (never in git, the exe or a player's config). Everything downstream (the check
reply, the gate plugin's log, the RustRCON panel) only ever sees this keyed id, so a leaked log can't be
matched against a PC's MachineGuid without the key. A new key gives every PC a new id: old links age out.
The `rustorigin-pc-v1:` prefix versions the scheme.

**Contested pairs.** Sessions are keyed by (SteamID, IP) and the SteamID is only a claim, so someone behind
the same public IP as a player could open sessions in that player's name with their own PC. When a fresh
session of a pair is replaced by one with another device (or none), the new session is *contested*: it
reports no device, isn't counted in `hw_accounts`, and stays contested while sessions of that pair keep
fighting. Once the pair has been quiet for a ttl, a new session is trusted again.

**Ban evasion (RustRCON panel).** The panel reads the device id from OriginSession's join line, keeps it on
the player record, and checks it against banned accounts. A same-PC match to an active ban is the only
launcher signal that acts by itself: by default it **kicks and opens a case for an admin**, configurable to
review-only or to a ban as long as the linked one, and it starts in **shadow mode** (the case says what would
have happened; nothing is done). IP, name and family-share links only ever open a case; private and
carrier-NAT addresses link nobody. An admin's "false alarm" on the case clears the link. Setup and config:
"Ban evasion by PC" in the RustRCON README.

Limits, stated plainly: the device id is a claim from a machine the player controls. Leaving it out,
skipping the launcher (until slice 7 requires a session) or changing the MachineGuid hides a link; a match
is good evidence, a missing match proves nothing. Shared family PCs, LAN cafés and cloned Windows images
without sysprep share one id, which is why the default is a kick plus a human decision, not a ban. A player
who shares the victim's IP and holds a session in their name while the victim plays *without* the launcher
can still put their PC on that account; requiring a session (slice 7) closes most of that. The SteamID
itself is only as trustworthy as the game server's Steam authentication.

## Binding and abuse cases

- **Sessions are keyed by (SteamID, IP), and several may exist per SteamID.** A session opened from
  another IP never replaces or invalidates a player's own session. Claiming someone else's SteamID from
  your own IP therefore cannot get that player kicked.
- **Shared IPs (NAT, LAN, family).** Every player behind the address still needs a session for their own
  SteamID. One honest launcher cannot vouch for a second account on the same IP.
- **Rate limits** on `POST /v1/session` per IP, and a cap on sessions per IP, keep the service small under
  abuse.
- **Session theft.** The key never leaves the launcher process and is only sent over TLS. A stolen key
  still only works from the original IP.
- **Hardware id.** Not part of the binding: two sessions with the same `hw` are both valid. It only adds
  `hw_accounts` to the check reply, for staff, and (slice 8) the device id the panel's ban-evasion check uses.
- **Planting a device on someone else's account.** A pair taken over by another device is contested and
  reports none (see [Device id](#device-id-slice-8)).

## Rollout

1. **Prerequisites:** the public session address (`ac.rustorigin.com`, TLS) is live and has an **A record
   only**: the game connects over IPv4, so a launcher reaching the service over IPv6 would come from
   another address and read as `mismatch`. A launcher release with `AcSessionUrl` set has reached players
   (it is mandatory through self-update). `AC_HW_KEY` is set.
2. **Shadow** (OriginSession 0.3.0 default, `Enforce` false): the gate logs every status, and a
   `would-kick` line for each player who stayed without a usable session for the grace period. The
   launcher never blocks PLAY when the service cannot be reached.
3. **Measure:** `would-kick` lines against joins (the `session` console command counts both). Look at
   who they are: players on an old launcher, players behind NAT that gives their HTTPS and game traffic
   different addresses (`mismatch`), staff who test without the launcher (give them `originsession.bypass`).
4. **Enforce** when nearly every join has a session: `session.enforce on`. A player with `none`, `stale`
   or `mismatch` (the last can be switched off) for `GraceSeconds` (120) is kicked with a message pointing
   at the launcher. `session.enforce off` rolls it back at once. If the service itself can't be asked
   (`error`), nobody is kicked: an outage lets everyone play rather than emptying the server.

## Privacy

What leaves the player's PC: the SteamID, the launcher version, heartbeat timing, whether the game is
running, the labels of matched signals (`tool:<id>`, `client:modified:<file>`) and the hardware id (a
one-way hash of the Windows MachineGuid). Game files are hashed on the PC, and only the "modified" label is
sent, never a hash or file contents. There are no process lists or personal files.

The session service keeps sessions in memory only and forgets them 6 hours after their last heartbeat. Its
log carries counts only. The gate plugin's daily log records each join's status and labels with the
player's name and SteamID, the first 16 hex characters of the hardware id, and the other accounts seen on
the same PC, for staff review. **Those log files are not pruned yet**: add a retention limit before
production. The RustRCON panel keeps
each account's keyed device ids (at most 10) for 180 days after they were last seen
(`evasion.pcRetentionDays`), longer only on accounts with an active ban, since that is what a ban-evasion
match is made of. Raw MachineGuids and the launcher's own hash are kept nowhere. A one-time notice in the launcher, shown after the first session-enabled PLAY, says
what is sent.

## Build slices

1. **Protocol helpers + this document** (no behaviour change). Done.
2. **Session service** (`ac_session.py`, Python 3 stdlib only, plus `linux/rust-acsession.service`) with
   tests, including the launcher's exact bodies and signature as interop fixtures. Runs on the Linux dev
   copy; not deployed to prod.
3. **`OriginSession` gate plugin** (0.1.0), shadow mode. It checks every player at join and every 60 s,
   logs join status and status changes to `oxide/logs/OriginSession/`, and **never kicks**. Console
   `session` shows counters and online players; `session.check <steamid> <ip>` asks the service directly.
   It exposes `GetLauncherStatus` / `GetLauncherSignals` for other plugins. Tested on the Linux dev copy
   against the session service for every status, including "service down"; not deployed to prod.
4. **Launcher wiring.** `AcSessionUrl` in `launcher.cfg` (blank by default). `AcSessionClient` starts
   right after the game process starts, opens a session for the Steam account in the registry (waiting
   for Steam if needed), heartbeats until the game exits, retries with backoff, and reopens when the
   service refuses a heartbeat. It never blocks PLAY. Tested against a fake service and live against the
   dev `ac_session.py`. (Closing the launcher while playing used to end the heartbeats; slice 7 keeps it
   in the tray instead.)
5. **Evidence signals + the privacy notice.** Two kinds of labels go with every heartbeat:
   - `tool:<id>` when a process from the server's tool rules (`tools` in the session reply) is running.
     The service translates the id back to a name for staff. A compiled script with its own exe name is
     not caught.
   - `client:modified:<file>` / `client:missing:<file>` when a game file listed in `AcClientFile=`
     (size + SHA-256 of the hosted build, from `scripts/make_client_filehashes.ps1`) differs. These files
     are hashed once per launch.

   No process list, handle scan or memory read; only labels leave the PC. A one-time notice after the
   first session-enabled PLAY says what is sent. The gate plugin logs the labels as evidence; they never
   kick anyone. The tool list is the one part that is not public: it lives in `ac_tools.txt` on the
   server, and players see only rule numbers. Anyone with a session can still read the rules from the
   reply, so it is out of plain sight, not secret.
6. **Hardware id** (alt-account signal, review only). The launcher sends `hw` with every session request
   (see [Hardware id](#hardware-id-slice-6)). The service indexes sessions by it and answers `hw` and
   `hw_accounts` in the check reply. OriginSession 0.2.0 adds `pc <id>` to the join line, logs
   `shared-pc` when another account turns up on the same PC, shows both in `session`, and exposes
   `GetLauncherPc` / `GetLauncherSharedAccounts`. It never kicks. Tested: the launcher against a reference
   vector computed independently, the service's interop fixture with the launcher's exact body, and the
   plugin compiled with C# 6 against the dev server's DLLs; not yet run on the dev server.
7. **Enforcement switch.** OriginSession 0.3.0: with `Enforce` on, a player without a fresh session for
   this SteamID + IP (`none`, `stale`, and `mismatch` unless `KickMismatch` is off) for `GraceSeconds` is
   kicked; the join is looked at again right when the grace ends, then every re-check (60 s). `error`
   never kicks. `originsession.bypass` exempts staff. `session.enforce on|off` switches it and saves the
   config. Off by default: shadow mode logs `would-kick` instead. The launcher keeps the session alive
   for honest players:
   - closing the window while the game runs hides it to the tray (with a notice) and the launcher quits
     when the game exits; tray > Quit still quits at once;
   - a game of ours running without a session (the launcher restarted by a self-update or a crash, or
     opened after the game) gets one within about 10 s;
   - the session follows the game rather than only the process the launcher started, so a client that
     hands over to a second process keeps its session.

   What it does not do: prove the client is clean, or stop a reimplementation of this open protocol
   (see [Goal and limits](#goal-and-limits)). It makes "start `RustClient.exe` on its own" stop working,
   which is what most launcher-skipping is. Tested: the launcher's session tests (including `Running`),
   the launcher and the plugin compiled (C# 6 against the dev server's DLLs). Not yet run on the dev
   server; the tray and adopt behaviour needs a manual check there.
8. **Device id + ban evasion** (this repo unchanged). `ac_session.py` keys the hardware id with `AC_HW_KEY`
   and marks contested pairs; OriginSession 0.2.1 logs `pc contested`; the RustRCON panel stores device ids
   from the join line, links same-PC accounts, and on a match to an active ban kicks + opens a case (default),
   reviews only, or bans, starting in shadow mode, with audit entries and retention. Tested: the service's
   unit tests (keying, contested takeovers in both orders), the panel's link tests (join-line parsing against
   forged names, IP-only never acting, false-alarm clearing, retention) and the real panel end to end against
   a fake RCON server in shadow, kick, ban and cleared modes; the plugin compiled with C# 6 against the dev
   server's DLLs. Not yet run on the dev server.
